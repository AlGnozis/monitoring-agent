# Product Vision — monitoring-agent

## Проблема

Продемонстрировать навыки **LLM-инженера** на позицию Python-разработчик (AI-агент) в Сбере через работающий **standalone-агент мониторинга**, реализующий типовой сценарий лида end-to-end: «пост в ленте → инцидент → RAG → владелец → заявка → письмо».

## Целевой пользователь

**Технический ревьюер / член команды лида** (один или несколько):

- Senior+ инженер с AI-фокусом, читает Python код профессионально.
- Оценивает: архитектуру, код-стиль, инженерную дисциплину, понимание production-нюансов.
- Точки касания с проектом:
  - **GitHub** — читает код, README, историю коммитов;
  - **Локальный запуск** — `docker-compose up` на своей машине;
  - **Видео-демо** или **live-демо** по экрану.
- Калибровка восприятия: ценит не отдельный «трюк», а **качество работы целиком** — включая видимый процесс инженерной дисциплины.

## Уникальная ценность

> Вместо разработки агента с нуля — **переиспользование обкатанных в продакшне паттернов AI-Factory** (RAG/E5/FAISS, GigaChat-клиент с кэшем токена, polling-loop) как production-ready ядро, обёрнутое в standalone-демо с явной observability, идемпотентностью и graceful degradation.

Демонстрирует одновременно **глубину работы с боевой кодовой базой** и **способность извлечь и переупаковать паттерны** в самостоятельный сервис.

## Метрика успеха MVP

**Один наблюдаемый факт «получилось»:**

> `docker-compose up` запускает агент; `POST /trigger` с записью из `fake_feed.json` за ≤ 30 секунд возвращает HTTP 200 и приводит к появлению:
> - **1 `EventRecord`** в SQLite со статусом `DONE`;
> - **1 ticket** `DEMO-001` в mock-Jira (SQLite-store; схема `DEMO-{seq:03d}`);
> - **1 письмо** `.eml` в `outbox/` владельцу затронутой системы из `owners.yaml`.
>
> Повторный запрос с тем же `event_hash` **не плодит дубликатов** (идемпотентность подтверждена в e2e-тесте).

После этого — публикация на GitHub + demo-видео ≤ 3 минуты.

## Anti-goals (что НЕ делаем — никогда или сейчас)

1. **НЕ** делаем реальные интеграции с Jira / SMTP / Slack — только mock-адаптеры с `Protocol` (production-ready форма, реальный коннектор — задел на будущее).
2. **НЕ** разворачиваем полный Django + Kafka стек — standalone-сервис на FastAPI + LangGraph.
3. **НЕ** делаем UI / админку / KB-builder web-интерфейс — только REST-эндпоинт `/trigger` + CLI seeding KB.
4. **НЕ** делаем real-time updates / WebSocket / push — синхронный `POST /trigger` + polling daemon для фидов.
5. **НЕ** делаем мультитенантность / RBAC / auth — один технический пользователь, никаких ролей.
6. **НЕ** включаем `ragas` в основные dependencies — bonus-фича за extra-флагом `[eval]` в `pyproject.toml` (`pip install -e ".[eval]"`).
7. **НЕ** делаем мобильную версию / responsive UI — UI отсутствует как класс.
8. **НЕ** работаем с реальными внутренними данными Сбера — только синтетика «Сбер-like» (платёжный шлюз, КИБ, СБОЛ, KYC).
9. **НЕ** оптимизируем под бесконечное полирование — критерий «готово к показу» (см. Метрика успеха) останавливает работу.

## Главные риски и митигации

| Риск | Вероятность | Митигация |
|---|---|---|
| GigaChat structured output ломается на сложных схемах | Высокая | Плоские Pydantic-схемы (нет `anyOf`, всегда `items`/`properties`); fallback-парсер если вернулся невалидный JSON; покрытие unit-тестами триажа на фиксtures |
| Ревьюер запускает на не-Mac машине — `docker-compose up` падает | Средняя | Проверка на чистой машине через GitHub Codespaces или devcontainer; README с двумя сценариями (dev / demo); явный `python:3.12-slim` в Dockerfile |
| Переиспользование из AI-Factory создаёт coupling, который сложно обосновать ревьюеру | Средняя | Каждый перенесённый паттерн — комментарий в коде со ссылкой на источник + причиной; **никаких прямых импортов из `ai-factory/`** — только адаптация |
| WOW-фактор «качество целиком» расплывчатый — может не выстрелить | Средняя | Делаем явные точки внимания: `CLAUDE.md` с Behavioral defaults в корне репо, `docs/ARCHITECTURE.md` с графом узлов, eval-цифры в README |
| Нет дедлайна → бесконечное полирование | Низкая (ловится критерием) | Жёсткий критерий «готово к показу» в Метрике успеха + checkpoint в `docs/iteration-1.md` |

## Принципы продукта

1. **Production-mindset, но честно minimal.** Идемпотентность, observability, graceful degradation — есть. Лишних фич нет.
2. **Видимый процесс.** `CLAUDE.md` с Behavioral defaults, `docs/`, README, история коммитов — это **часть продукта, не «вспомогательное»**. WOW-фактор ревьюера во многом отсюда.
3. **Каждое переиспользование обосновано.** Если копируем паттерн из AI-Factory — рядом в коде ссылка и причина. Источник переиспользования — `docs/REUSED-FROM-AI-FACTORY.md`.
4. **Mock через `Protocol`, не if/else.** Адаптеры — production-ready форма (`TicketAdapter`, `NotifyAdapter`), mock — конкретная реализация. Реальный коннектор — задел, добавляется без рефакторинга.
5. **Git с первого commit.** Conventional commits (`feat:`, `fix:`, `docs:`, `refactor:`), чистая линейная история, README на каждом этапе. Репозиторий — deliverable.
